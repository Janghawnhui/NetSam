# NetSamLite

PC에 설치된 SW/HW 정보를 에이전트로 수집하고, 서버에서 정규화·라이선스 비교·리포트를 하는 미니 SAM(Software Asset Management) 솔루션입니다. 상용 SAM 솔루션의 동작 원리를 직접 구현하며 이해하는 것이 목적이고, 완성도보다 이해를 우선했습니다.

Phase 1~6을 거쳐 수집 에이전트 → 서버 API/DB → SW 정규화 → 라이선스 매칭 → 대시보드/정책 → 서비스화까지 전부 구현했습니다.

---

## 구조도

```
NetSamLite.sln(x)
├─ src/
│  ├─ NetSamLite.Shared/        DTO, API 계약 (record 타입)
│  │   DeviceInfo, InstalledSoftware, InventoryReport
│  │
│  ├─ NetSamLite.Agent/         Worker Service (Windows 서비스 가능)
│  │   Collectors/              레지스트리/WMI 수집기 (읽기 전용)
│  │   Sending/                 전송 + 재시도/백오프 + 로컬 큐
│  │
│  ├─ NetSamLite.Server/        ASP.NET Core Web API + EF Core(SQLite)
│  │   Data/                    Device/InstalledSoftwareSnapshot/
│  │                            SoftwareChangeEvent/License/
│  │                            ProhibitedSoftware 엔티티
│  │   Inventory/               수집 결과 수신 + 이전 스냅샷과 diff
│  │   Normalization/           규칙 엔진 (JSON 규칙 파일 기반)
│  │   Licensing/                라이선스 매칭
│  │   Policy/                  금지 SW 알림
│  │   Devices/                 장치 목록/상세 조회
│  │   Reports/                 CSV 리포트
│  │
│  └─ NetSamLite.Web/           Blazor Server 대시보드
│      Components/Pages/        장치 목록, SW 현황, 라이선스 현황,
│                                금지 SW 알림
│
├─ tests/
│  ├─ NetSamLite.Agent.Tests/
│  └─ NetSamLite.Server.Tests/
│
├─ samples/                     테스트용 수집 결과 JSON
└─ docs/                        backlog.md, learning-log.md, service-install.md
```

**의존 방향**: `Agent → Shared ← Server ← Web`. Agent와 Server는 서로 직접 참조하지 않고(별도 머신에서 돌 수 있어야 해서) HTTP로만 통신합니다. Web은 Server를 **직접 참조**합니다(같은 머신에 같이 배포되는 대시보드라 HTTP 왕복 없이 Server의 서비스/DbContext를 그대로 재사용).

## 실행 방법

```powershell
dotnet build                                   # 전체 빌드
dotnet test                                    # 전체 테스트

# 1회 수집 (Phase 1부터 가능, 서비스 모드와 무관)
dotnet run --project src/NetSamLite.Agent -- --once --out samples/my-pc.json

# 서버 — 최초 1회 연결 문자열 설정 후 실행
dotnet user-secrets set "ConnectionStrings:NetSamLite" "Data Source=netsamlite.db" --project src/NetSamLite.Server
dotnet run --project src/NetSamLite.Server

# 대시보드 — 역시 연결 문자열 설정(Server와 같은 DB 파일을 가리킴) 후 실행
dotnet user-secrets set "ConnectionStrings:NetSamLite" "Data Source=../NetSamLite.Server/netsamlite.db" --project src/NetSamLite.Web
dotnet run --project src/NetSamLite.Web

# 에이전트를 서비스 모드로(인자 없이 실행) — 설정된 주기로 수집·전송 반복
dotnet run --project src/NetSamLite.Agent

# DB 마이그레이션 추가
dotnet ef migrations add <이름> --project src/NetSamLite.Server
```

Windows 서비스로 실제 등록/삭제하는 명령은 `docs/service-install.md`에 정리돼 있습니다(관리자 권한 필요라 이 세션에서는 실행하지 않았습니다).

## Phase별 핵심 설계 결정과 이유

### Phase 1 — 수집 에이전트

- **레지스트리는 항상 읽기 전용으로만 연다** (`OpenSubKey(..., writable: false)`). 쓰기·삭제·프로세스 종료 코드는 범위 밖.
- **`HKLM`을 64비트/32비트 뷰 둘 다 연다.** 뷰를 지정하지 않으면 Agent 프로세스 자신의 비트니스에 해당하는 쪽만 보여서(WOW64 리다이렉션), 둘 다 명시해야 네이티브 64비트 앱과 32비트 앱을 모두 수집할 수 있다. 경로에 `WOW6432Node`를 직접 넣지 않고 `RegistryView.Registry32`에게 리다이렉션을 맡긴다.
- **`Win32_Product` WMI 클래스는 쓰지 않는다.** 조회만 해도 MSI 무결성 검사·재구성이 일어나 느리고 부작용이 있어서, 설치 SW는 레지스트리 Uninstall 키로만 수집한다.
- **장치 식별자는 BIOS 시리얼 + 컴퓨터 이름.** 시리얼이 비거나 `"To be filled by O.E.M."` 같은 더미 값이면 `MachineGuid`로 대체한다.
- **예외 격리를 여러 층으로 둔다.** 레지스트리 하위 키 1개, 소스(hive/view) 1개, WMI 클래스 1개가 실패해도 나머지는 계속 수집된다 — 한 군데 문제로 전체 수집이 멈추면 안 된다는 원칙을 처음부터 끝까지 지켰다.

### Phase 2 — 서버 API + DB

- **"현재 상태"와 "변화 이력"을 테이블로 분리.** `InstalledSoftwareSnapshot`(지금 설치돼 있다고 알려진 것)과 `SoftwareChangeEvent`(설치/삭제가 언제 일어났는지)를 따로 둬서, "지금 뭐가 깔려있나"와 "뭐가 바뀌었나"를 각각 단순하게 조회할 수 있게 했다.
- **같은 요청 안의 중복 항목은 "마지막 값이 이긴다".** Agent가 32/64비트 중복 제거를 안 하므로, 서버가 한 요청 안에서 같은 이름이 여러 번 오는 경우를 흡수해야 유니크 제약 위반으로 전체 수집이 실패하는 걸 막을 수 있었다.
- **입력 검증 누락이 실제 버그로 이어짐을 직접 겪었다.** `Device`가 없는 요청을 검증 없이 처리하면 500이 나는 걸 리뷰에서 발견 → 필수 필드 검증 후 400으로 응답하도록 수정.

### Phase 3 — SW 정규화

- **규칙을 코드가 아니라 JSON 데이터로 분리.** `normalization-rules.json`의 규칙 그룹(제외 → 별칭 테이블 → 제품별 패턴 → 공통 정리) 순서가 그대로 적용 순서가 된다.
- **의미와 무관한 청소(유니코드 정규화, 공백 trim/축약)는 규칙화하지 않고 엔진에 고정.** 모든 입력에 예외 없이 똑같이 적용되는 동작이라 데이터로 표현할 이유가 없었다.
- **"제외"와 "분류 후 라이선스 대상에서만 뺌"을 구분.** 예를 들어 무료 런타임류 제품은 완전히 버리는 게 아니라 `Licensable=false`로 태그해서 화면에는 보이지만 라이선스 비교에는 안 들어가게 했다 — 삭제와 "보이되 집계에서 뺀다"는 서로 다른 요구라서.
- **미분류 비율을 실제 샘플로 측정했다.** 규칙 5개만으로는 수집된 SW의 대부분이 미분류로 남는다는 걸 숫자로 확인했고, 이게 "정규화는 규칙 테이블에 계속 투자해야 하는 영역"이라는 걸 보여준다.

### Phase 4 — 라이선스 매칭

- **라이선스 데이터는 JSON 설정 파일이 아니라 DB + API(CRUD)로.** 정규화 규칙과 달리 라이선스는 구매·만료로 계속 바뀌는 "운영 데이터"라서, 대시보드가 추가/수정/삭제할 수 있는 구조가 자연스럽다.
- **설치 수는 (디바이스, 제품명) 기준으로 먼저 유니크화한 뒤 센다.** 한 PC에 같은 제품이 중복 등록된 경우(설치 범위 차이 등)로 설치 수가 부풀려지는 걸 막는다.
- **미분류 SW는 매칭에서 기본 제외.** 원본 이름이 제각각인 미분류 항목을 그대로 집계하면 "라이선스 0건짜리 제품이 여러 개 있다"는 식의 거짓 경보가 난다. 분류가 안 된 상태에서는 애초에 판단 근거가 없다고 보고 별도 섹션으로만 보여준다.
- **항목 단위 예외 처리 + 실패 건수 노출.** 정규화 규칙 하나가 잘못돼도 리포트 전체가 깨지지 않고, 몇 건이 처리 실패했는지(`FailedCount`)를 응답에 그대로 노출해서 "조용히 누락"되는 걸 막는다.

### Phase 5 — 대시보드·정책

- **Blazor Server + Server 직접 참조.** 대시보드가 별도 API 클라이언트 레이어 없이 Server의 서비스(`LicenseMatchingService` 등)를 DI로 그대로 주입받아 쓴다 — 같은 머신에 같이 배포되는 전제라 HTTP 왕복과 DTO 중복을 둘 다 피할 수 있다.
- **top-level statements를 쓰는 두 ASP.NET Core 프로젝트가 서로 참조할 때의 이름 충돌.** Server의 암묵적 `Program` 클래스가 기본적으로 public이라 Web이 참조하면 Web 자신의 `Program`과 충돌한다 — `internal`로 내리고, 테스트용 `WebApplicationFactory<T>`에는 이름이 안 겹치는 별도 마커 타입을 뒀다(`T`는 타입 자체가 아니라 "그 타입이 속한 어셈블리"를 찾는 용도일 뿐이라는 점을 활용).
- **금지 SW 중복 판정을 위해 정규화된 키 컬럼을 따로 둠.** SQLite의 `NOCASE` 콜레이션은 ASCII 대소문자만 다뤄서 비ASCII 제품명에는 효과가 없다. 대신 "Trim + 공백 축약 + 대문자화"를 한 C# 함수에서 처리해 별도 컬럼에 저장하고, 그 컬럼에 유니크 인덱스를 걸어 **앱 로직과 DB 제약이 항상 같은 기준**을 쓰게 만들었다.
- **같은 정규화 키를 쓰는 모든 경로를 다 찾아 바꿔야 한다.** "등록" 경로만 새 키로 바꾸고 "알림 매칭" 경로를 놓쳐서, 공백이 불규칙한 이름을 등록하면 알림이 영원히 안 뜨는 버그가 실제로 났다. 비교 로직을 여러 곳에 흩어두면 이런 틈이 생긴다는 걸 직접 겪었다.
- **CSV 내보내기에 수식 인젝션 방어.** 제품명은 설치 프로그램이 임의로 정한 문자열이라, `=`/`+`/`-`/`@`로 시작하면 스프레드시트 프로그램에서 수식으로 실행될 수 있어 앞에 인용부호를 붙여 문자열로 강제한다.

### Phase 6 — 서비스화

- **`UseWindowsService()`로 코드 분기 없이 서비스/콘솔 양쪽 지원.** SCM 밑에서 실행될 때만 서비스로 동작하고, 콘솔에서 직접 실행하면 평소처럼 동작한다.
- **jitter는 시작할 때 한 번만.** 여러 PC가 같은 시각에 한꺼번에 서버로 몰리는 걸 막으면 되고, 한 번 흩어놓으면 이후 주기들도 각자 시작 시각 기준으로 계속 흩어진 상태를 유지하므로 매 사이클마다 다시 넣을 필요가 없다.
- **재시도/큐는 순서를 지킨다.** 서버가 꺼져 있다 돌아왔을 때, 방금 수집한 새 리포트가 오래된 큐보다 먼저 도착하면 서버가 설치/삭제 이력을 거꾸로 기록한다. 그래서 큐를 오래된 것부터 전부 비운 뒤에만 새 리포트를 보낸다.
- **다만 영원히 실패하는 항목이 전체를 막으면 안 된다(head-of-line blocking).** 재시도 상한을 넘긴 항목은 포기하고 `failed` 폴더로 옮겨서, 그 뒤에 쌓인 리포트들은 계속 전송을 시도할 수 있게 했다. "순서 보장"과 "한 항목이 전체를 막지 않게"를 동시에 만족시키려면 두 규칙을 구분해서 조합해야 했다.
- **큐 파일은 임시 파일 + `File.Move`로 원자적으로 쓴다.** 쓰는 도중 프로세스가 죽어도 반쪼가리 파일이 최종 경로에 남지 않는다.
- **SYSTEM 계정에서 사용자별 설치 SW는 `HKCU` 대신 `HKEY_USERS`를 열거.** 서비스가 SYSTEM으로 돌면 `HKCU`가 SYSTEM 자신의 프로필이 되어버린다. 이미 로드돼 있는 사용자 하이브만 조회하고(하이브를 추가로 로드/언로드하지 않음), SID 정규식으로 실제 사용자 계정만 걸러낸다 — 읽기 전용 원칙을 지키면서 수집 범위를 넓힌 방법. 수집 시점에 로그인해 있는 사용자만 보인다는 한계는 그대로 남는다.

## 배운 점

Phase를 거치며 반복해서 마주친 일반적인 개념들입니다. 자세한 내용과 날짜별 기록은 `docs/learning-log.md`에 있습니다.

- **WOW64 레지스트리 리다이렉션**은 `HKLM`뿐 아니라 `HKCU`/`HKEY_USERS`에도 똑같이 적용된다 — 루트 키 종류와 무관하게 뷰(64/32비트) 단위로 동작한다.
- **DB 콜레이션은 "DB만의 비교 규칙"일 뿐이다.** 앱 코드가 그 규칙을 모르면 "앱은 대소문자 무시, DB는 구분" 같은 불일치가 생기고, 동시성 안전장치(유니크 제약 위반 캐치)가 바로 그 지점에서 뚫릴 수 있다. 정규화 결과를 별도 컬럼에 저장해 앱과 DB가 같은 함수의 결과값을 보게 하는 게 더 안전했다.
- **System.Text.Json의 record 역직렬화는 nullable을 런타임에 강제하지 않는다.** JSON에 없는 속성은 예외 없이 기본값(참조형이면 null)으로 채워진다 — 데이터 포맷을 바꿀 때 "구버전 파일을 읽으면 조용히 null이 들어간다"는 걸 염두에 둬야 한다.
- **Head-of-line blocking**: 순서를 지키려고 "앞이 성공해야 다음으로" 규칙을 걸면, 앞 항목이 영원히 실패하는 경우까지 대비하지 않으면 전체가 멈춘다. 포기할 기준(재시도 상한)이 필요하다.
- **원자적 파일 쓰기**: 임시 파일에 쓰고 같은 볼륨에서 `File.Move`로 교체하면, 쓰는 도중 프로세스가 죽어도 중간 상태가 보이지 않는다.
- **Dead-letter 큐**: 정상 처리가 불가능해진 항목을 삭제하지 않고 별도 위치로 격리해두면, 나중에 사람이 원인을 들여다보고 필요하면 수동으로 재처리할 수 있다.
- **정규화 키(canonical key)와 표시용 원본 값은 분리해서 다룬다.** 비교/매칭/유니크 제약은 하나의 정규화 함수가 만든 키로 하고, 사용자에게 보여줄 때만 원본을 쓴다 — 비교 로직이 여러 곳에 흩어지면 "한 곳만 고치고 다른 곳을 놓치는" 버그가 생기기 쉽다.
- **예외 하나가 전체를 중단시키면 안 된다는 원칙은 레이어마다 반복해서 나타난다.** 레지스트리 하위 키, WMI 클래스, 정규화 규칙, 큐 항목, 사용자 하이브까지 — 항목 단위로 격리하고 나머지는 계속 진행하는 패턴이 거의 모든 Phase에 등장했다.
